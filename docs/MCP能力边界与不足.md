# MCP（GitHub 工具集）能力边界与不足

> 基于 2026-11-14 在本仓库完成 13 个提交的实际使用总结。
> 用途：优化 MCP 实现时的需求清单；也提醒后续会话「哪些事别指望 MCP」。

---

## 一、硬性能力缺失（根本做不到）

### 1. 无法执行本地 git 操作 ← 影响最大
- **缺**：`git merge` / `rebase` / `cherry-pick` / `stash` / 冲突解决
- **后果**：**同步上游这类核心工作完全做不了**。本次落后 173 提交 / 121 文件的同步，只能产出方案让用户手动执行。
- **GitHub 合并 API 也救不了**：`merge_pull` 只处理「能快进」的情况，代码冲突一律失败。
- **建议**：要么提供本地仓库绑定能力，要么明确把「同步上游」标记为不可委派任务。

### 2. 无法触发 `workflow_dispatch`
- **缺**：手动触发工作流的工具
- **现有**：只有 `rerun_workflow`，而它**只能重跑已存在的旧 commit**，无法让新提交参与构建。
- **后果**：本次为了触发构建，不得不额外提交一次有意义的改动（`CHANGELOG.md`）来产生 `push` 事件。

### 3. 无法读 Actions 运行日志正文的完整内容
- `get_job_logs` 有 `max_chars` 截断（默认只留尾部）。
- 构建失败时若关键报错在中段，可能拿不到。建议支持分段读取或 `grep` 语义。

### 4. 无法读取文件的部分内容 / 精确行范围
- `get_file` 返回整文件（受 1MB 限制），大文件**会因超限而拿不到 `content` 字段**。
- 本次 `SettingsNormalization.kt` 就踩到过：匿名 API 返回不含 `content`，只能改用 MCP 的 `get_file`。
- **建议**：支持 `startLine`/`endLine` 或字节范围参数。

### 5. 无法执行任何构建 / 编译验证
- 只能读代码，不能编译。所有「改完能不能编过」都要靠 CI 或用户本地验证。
- **后果**：改动只能通过 CI 回合确认；UI 视觉效果更是完全不可见。

## 二、行为陷阱（能用，但容易误判）

### 6. `raw.githubusercontent.com` 的 CDN 缓存
- **现象**：刚通过 API 提交的文件，raw 链接仍返回**旧内容**。
- **本次事故**：一度误判「AiHubMix 改动丢失」，实际是用 raw 校验导致的假警报。
- **正确做法**：一律用 `gh_get_file` / `gh_get_content_sha`（走 API，无缓存）。
- **建议**：在工具描述里显式警告，或提供 `get_file_fresh`。

### 7. `put_file` 的 `sha` 校验会失败（即使内容没变）
- **现象**：用从 `list_tree` 拿到的旧 sha 提交，返回 `409 does not match`；重新 `get_content_sha` 后新 sha 与旧的不同，但**文件内容完全一致**。
- **原因**：分支 rebase / 内部重建导致 blob 重新计算。
- **建议**：`put_file` 支持 `sha: "auto"` 自动获取最新，或冲突时自动重试一次。

### 8. `compare_commits` 的 base 必须存在于目标仓库
- 本次拿 fork 独有提交当 base 去 compare 上游，返回的是无意义结果（`ahead_by: 38` 其实是上游相对 merge base 的提交数）。
- **建议**：base 不在目标仓库时直接报错，而不是静默返回误导性数据。

### 9. 匿名 API 与 MCP 认证 API 的配额差异
- 沙箱里 `curl api.github.com` 是**匿名**（60 次/小时，很快耗尽）。
- MCP 走认证（5000 次/小时）。
- **建议**：文档明确「沙箱 curl 不要用于 GitHub API」。

### 10. `list_workflow_runs` / `list_repos` 返回体极大
- 单次响应常达 60k~470k 字符，被强制截断存文件。
- **建议**：默认精简字段（像 `fields` 参数那样），或用分页 + 字段选择。

## 三、本次实际踩坑流水（可作为回归用例）

| # | 现象 | 根因 | 代价 |
|---|---|---|---|
| 1 | 提交后查不到构建 | Actions 被 GitHub 暂停（配额） | 误判为「API 提交不触发 CI」，写进文档后需返工纠正 |
| 2 | `put_file` 409 | 旧 sha（blob 重建） | 1 次失败重试 |
| 3 | 改动的文件「消失」 | raw CDN 缓存 | 虚惊一场，需二次验证 |
| 4 | 子 Agent 模型选择无底色块 | 用了 `ModelSelector` 而非 `ModelField` | 用户反馈后返工 1 次 |
| 5 | Skill 页面「按钮太挤」改错方向 | 用户指垂直间距，改了水平间距 | 返工 1 次 |
| 6 | 上游同步做不了 | 无 git 能力 | 只能交付方案文档 |

> 第 4、5 条不是 MCP 的锅，但说明**缺少 UI 预览能力**会显著增加返工。

## 四、优化优先级建议

| 优先级 | 需求 | 理由 |
|---|---|---|
| P0 | 本地 git / 冲突解决能力 | 否则 fork 同步类任务永远不可委派 |
| P0 | `workflow_dispatch` 触发 | 每次都要靠「造一次提交」绕路，很脏 |
| P1 | 文件按行范围读取 | 大文件拿不到内容，被迫用 curl 绕 |
| P1 | `put_file` 自动 sha / 冲突重试 | 高频摩擦点 |
| P2 | 工具描述里标注 raw 缓存陷阱 | 避免误导性验证 |
| P2 | 列表类接口默认精简字段 | 响应体过大，被迫落盘再 grep |
| P3 | UI 预览 / 截图能力 | 减少样式类返工 |

---

## 五、对后续会话的行动准则

1. **验证文件内容只用 `gh_get_file`**，不要用 raw 链接。
2. **遇到「提交了不构建」**，先查 Actions 是否被暂停，别急着怀疑提交方式。
3. **`put_file` 报 409 时**，重新 `get_content_sha` 再试，不要怀疑自己的内容。
4. **改 UI 前**，先去同类页面找现成的标准组件（如 `SettingModelPage` 的 `modelItem`），别自己拼。
5. **用户说「太挤/太近」时**，先分清是水平还是垂直，问清楚再改。
6. **同步上游**：直接告诉用户需要本地执行，并给出精确的冲突清单，不要假装能代劳。
