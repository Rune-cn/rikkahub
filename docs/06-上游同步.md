# 06 · 上游同步（fork 维护流程）

## 1. 标准流程

```bash
cd /workspace/rikkahub
git fetch upstream                    # 拉上游新提交
git rebase upstream/master            # 本地 master 重放 fork 提交到上游最新
# 冲突 → 逐个解决 → git add <file> → GIT_EDITOR=true git rebase --continue
git push --force-with-lease origin master   # rebase 改了历史，必须 force
```
- PAT 推送（无 token 时）：
  ```bash
  TOKEN=...  # 在 shell 环境变量里，文档不落盘
  git -c http.extraheader="AUTHORIZATION: basic $(printf 'x-access-token:%s' "$TOKEN" | base64 -w0)" push --force-with-lease origin master
  ```
- 少量上游提交不想重放时可 `git cherry-pick`（先同步后新增的场景）。

## 2. 冲突高发区（做过 128 提交大同步的实际经验）

| 文件 | 冲突原因 | 处理原则 |
|---|---|---|
| `data/datastore/PreferencesStore.kt` | 上游拆分设置文件 | fork 字段迁移到 Settings.kt + SETTINGS_FIELDS，PreferencesStore 不塞旧 Settings 类 |
| `data/ai/*`（GenerationLoop 等） | 上游删除/重构 | 接受删除，按新 API（04）重接功能 |
| `service/ChatService.kt` | 上游 runTurn/session 重构 | 保留 fork 行为（节流落库/子 Agent 写入），结构跟上游 |
| `ui/pages/setting/*`（各设置页） | 上游 MD3 重写 | VM 的 updateSettings 用上游版（去重），页面结构跟上游 |
| `strings.xml` | 双方都加字符串 | 去重（保留第一个） |
| `.github/workflows/daily-build.yml` | 上游改 flavor | 以 assembleGithubRelease + apk/github/release 为准 |

## 4. 同步后强制检查清单

1. `git grep -l '^<<<<<<< '` 全树无残留标记。
2. `app/build.gradle.kts` 版本号不被上游覆盖（保持 fork 的 appVersion/appVersionCode）。
3. 构建：push 后看 Actions（失败→下载 logs→`grep "e: file"`→修→再 push，循环）。
4. fork 功能抽查：设置搜索展开、扩展管理入口、子 Agent 工具、运行日志页。
5. 更新本目录与 AI_DEVELOPMENT.md 的同步状态描述（基线 commit、新坑）。
